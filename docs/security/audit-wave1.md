## ۱. یافته‌های امنیتی

### S-01 — بالا — صفحه‌های SVG مصحف از `raw.githubusercontent.com` زنده سرو می‌شوند
`apps/web/lib/quran-svg-page.ts` صفحه‌های چاپی مصحف را از
`https://raw.githubusercontent.com/quran-ws/quran-svg/main/mushafs/...` می‌گیرد
(پروکسی هم‌خاست `/api/quran-svg/...` فقط یک لایهٔ میان‌بُر است و خودش همان
آدرس را fetch می‌کند). سه مشکل جدی:

1. **سلامت متن مقدس:** محتوای قرآن از شاخهٔ `main` یک ریپوی خارجی **بدون
   نسخهٔ قفل‌شده** (بدون commit-pin، بدون هشینگ) رندر می‌شود. هر تغییر در آن
   ریپو، متن صفحه‌های قرآن این سایت را بی‌صدا عوض می‌کند.
2. **دسترس‌پذیری در ایران:** خود کد می‌نویسد reachability از ایران «UNVERIFIED»
   است؛ در بلوک شدن CDN، همهٔ صفحه‌ها به متن‌پس‌فرض سقوط می‌کنند.
3. **پرفورمنس:** هر صفحهٔ SVG ~۱۸۵KB تا ۶۱۸KB **بدون فشرده‌سازی** (نسخهٔ
   brotli وجود دارد ولی raw GitHub آن را با `Content-Encoding` نمی‌فرستد؛
   پروکسی هم همان باینری خام را برمی‌گرداند).

**اقدام:** رفع به مالک قلم واگذار شد — ایجنت «مصحف و قرآن» (خودمیزبانی فایل‌ها
روی اورijin خودمان + brotli + پین نسخه/هاش) با همکاری «بک‌اند/دواپس»
(هاستینگ استاتیک). جزئیات در §۴.

### S-02 — متوسط — سایت وب هیچ هدر امنیتی ندارد (رفع‌شده در این برنچ)
بررسی زندهٔ `academy.matoridi.ir/fa/quran`: بدون `X-Frame-Options`، بدون
`X-Content-Type-Options`، بدون `Referrer-Policy`؛ هدر API (که از
`SecurityHeadersMiddleware` می‌آید) فقط در `api.matoridi.ir` دیده می‌شود.

**رفع در این برنچ:** سه هدر بالا در `apps/web/next.config.mjs` برای همهٔ
مسیرها اضافه شد. سایت خود را iframe نمی‌کند (دسکتاپ/موبایل از WebView URL
استفاده می‌کنند؛ iframeهای ویدیویی خروجی‌اند و تحت تأثیر نیستند)، پس
`DENY` ایمن است. HSTS عمداً اینجا گذاشته **نشد** (dev روی http سرو می‌شود؛
مالک HSTS پیکربرداری TLS است — S-05).

### S-03 — پایین — HSTS روی هر دو دامنهٔ زنده نیست
`api.matoridi.ir` و `academy.matoridi.ir` بدون `Strict-Transport-Security`
پاسخ می‌دهند. کد API این را عمداً به ingress/proxy واگذار کرده
(`SecurityHeadersMiddleware` در `apps/api/app/core/middleware.py`). تنظیم روی
nginx/Railway در اختیار «بک‌اند/دواپس» است (پیکربرداری، نه کد).

### S-04 — پایین — نشت `x-powered-by: Next.js` روی وب
اطلاعات‌نشتی جزئی؛ حذف با یک خط در middleware/nginx وب (قلم وب).

### S-05 — اطلاعاتی — CORS: درست پیکربندی شده
CORS فقط وقتی `CORS_ALLOW_ORIGINS` تنظیم باشد فعال است (پیش‌فرض: غیرفعال) —
`apps/api/app/main.py`. پیش‌فلایت زنده با `Origin: https://evil.example.com`
هیچ `Access-Control-Allow-Origin` برنمی‌گرداند (پوشنه رد می‌شود). ✅

### S-06 — اطلاعاتی — احراز هویت/نشست/2FA: مطابق قرارداد
- Argon2id برای رمز؛ access token ۱۵ دقیقهٔ HS256 با `jti`؛ refresh token
  opaque با هش SHA-256 در DB و rotation؛ claimهای امنیتی قابل بازنویسی از
  `extra` نیستند (`security.py`).
- 2FA = TOTP با ضد-replay (شمارندهٔ گام) + کدهای بازیابی یک‌بارمصرف؛
  scope `2fa_setup` فقط مسیرهای ثبت‌نام 2FA را باز می‌گذارد.
- Rate limiting توزیع‌شدهٔ Redis (`app/core/rate_limit.py`) با fail-closed؛
  کلاس حافظه‌ای قدیمی LEGACY است و هیچ مسیر productionی از آن استفاده
  **نمی‌کند** (FIX3-03). ✅
- رفتار زندهٔ rate-limit روی login عمداً تست نشد (خطر قفل حساب واقعی در
  محیط production).

### S-07 — اطلاعاتی — آپلود فایل: مطابق قرارداد §۷
پسوند + magic-byte + سقف حجم، خواندن جریانیِ capped
(`read_capped_upload`)؛ اسکن ویروس (ClamAV) به‌خاطر رم ۱ گیگ هاست فعلی
پارک شده است (محدودیت زیرساخت، در بریف — رفع آن کار دواپس هنگام ارتقا). ✅

### S-08 — پایین — CSP نداریم (وب و API)
CSP کامل روی Next.js نیازمند nonce برای اسکریپت‌های inline RSC است
(۱۰ اسکریپت inline در HTML صفحهٔ اول). پیاده‌سازی nonce در middleware وب
یک کار چندخطی-ولی-دقت‌طلب است → فاز ۵، قلم وب (تیکت در §۴).

### S-09 — OK — رمز/کلید در کد و تاریخچه
- درخت کاری: صفر یافته (اسکن الگوهای `sk-`/`ghp_`/`AKIA`/`xox`/JWT/
  private-key روی همهٔ کد و پیکربندی).
- تاریخچهٔ ۲۰۰ کامیت اخیر: صفر یافته (اسکن diff با الگوهای بالا).
- هیچ `.env` واقعی در هیچ کامیت ثبت نشده (فقط `.env.example`ها).
- `assert_production_secrets_ok` در استارتاپ production، secretهای
  placeholder/ضعیف را رد می‌کند و بدون کلیدهای الزامی بوت نمی‌شود.
- **محدودیت:** کل تاریخچهٔ ۸۶۳ کامیت اسکن نشد (gitleaks روی این ماشین قابل
  نصب نبود — شبکه به GitHub ناپایدار است؛ کلون partial/blob:none است).
  CI خود ریپو gitleaks/semgrep اجرا می‌کند؛ پیشنهاد: یک بار اسکن کامل
  تاریخچه روی runner سبز.

## ۲. خط‌باس پرفورمنس (اعداد «قبل»)

محیط اندازه‌گیری: این ماشین، ساعت ۲۰۲۶-11-26 ~03:00 UTC، ۵ تکرار برای هر URL.
اعداد از **سایت زندهٔ فعلی** (deploy فعلی، همان چیزی که کاربر می‌بیند).

### ۲.۱ صفحه‌ها (curl، بدون مرورگر — TTFB و حجم wire)

| URL | TTFB میانه | کل (میانه) | HTML در wire | HTML پس از decode | یادداشت |
|---|---|---|---|---|---|
| `academy.matoridi.ir/fa/` | **735ms** | 1.27s | 54.0KB | 303KB (۱۵۱KB آن اسکریپت inline RSC) | ۲ نوسان: 4.2s و 8.4s (cold start) |
| `academy.matoridi.ir/fa/quran` | **520ms** | 0.98s | 43.0KB | 174KB | ۱ نوسان 7.0s (cold start) |
| `/api/quran-svg/hafs/kfqc/svg/001.svg` | 516ms (گرم) / 924ms (سرد) | 0.99–1.42s | **185KB بدون فشرده‌سازی** | — | SVG صفحهٔ ۱ مصحف |
| `api.matoridi.ir/health` | ~515ms | — | 27B | — | — |
| `api.matoridi.ir/api/v1/home/sections?locale=fa` | ~510ms | ~650ms | 22KB (بدون gzip) | — | — |

### ۲.۲ باندل JS صفحهٔ اول (زنده)
- ۱۲ چانک خارجی، مجموع **225.6KB فشرده** (gzip) — بزرگ‌ترین‌ها: 71.8KB،
  44.1KB، 39.6KB، 21.4KB.
- ۱۰ اسکریپت inline در HTML: **151KB** (بزرگ‌ترین 93.6KB — payload ریزش
  RSC). این بزرگ‌ترین عامل چاقی HTML است: متن قابل‌مشاهدهٔ صفحه فقط ~7KB است.
- مقایسه با `docs/performance-budget.md` (بیلد لوکال اکتبر ۲۰۲۶): First Load
  JS بودجه‌شده 99.5KB؛ اندازهٔ زنده 225KB → deploy زنده یا بیلد متفاوت است یا
  باندل رشد کرده — نیازمند بررسی با مالک وب.

### ۲.۳ نتیجه‌گیری در برابر هدف «زیر ۲ ثانیه»
- **صفحهٔ اول:** TTFB 735ms + HTML 54KB + JS 226KB + فونت‌ها/تصاویر ≈ در
  اتصال خوب زیر ۲ ثانیه است، ولی در اتصال معمولی/متن‌مرکزی در مرز یا بالای
  آن؛ نوسان cold-start (تا 8.4s) تجربهٔ بدی می‌سازد.
- **مصحف:** بازدید اول = HTML 43KB + JS + **SVG 185KB خام** → به‌طور
  قابل‌اعتماد **بیش از ۲ ثانیه** در اتصال معمولی. با کاش ۱ سالهٔ
  `immutable` بازدیدهای بعدی خوب‌اند.
- **دو اهرم اصلی:** (۱) خودمیزبانی SVG مصحف با brotli (185KB → ~33KB
  بسته به صفحه) + pin نسخه؛ (۲) کاهش payload inline RSC/HTML صفحهٔ اول
  (151KB → هدف < 60KB).

### ۲.۴ کوئری‌ها / N+1
مسیرهای داغ کاربردی بررسی شدند:
- `home/service.get_home_sections`: ۲ کوئری (sections + theme) — بدون N+1. ✅
- `social/service.list_feed` / `list_comments`: صفحه‌بندی **cursor** + یک
  کوئری؛ `liked_post_ids` با `IN` گروهی. ✅
- ۳۱ حلقهٔ `for` که در پنجرهٔ ۸ خط بعدشان `await db.execute(select(...))`
  دیده می‌شود، به‌صورت خودکار فهرست شد؛ نمونه‌هایی که کاربری/داغ نبودند
  (admin 360، lms، hifz) برای بررسی دقیق‌تر به «تست و مستندات»/«بک‌اند»
  ارجاع می‌شوند. شمارش دقیق کوئری نیازمند اجرای لوکال با PostgreSQL است —
  در تسک bootstrap ایجنت بک‌اند (فاز ۰ او) پوشش می‌شود.
